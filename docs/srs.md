## 1. System Context (Контекст системи)

### 1.1 Призначення та межі (Scope)

Система реєструє факти видачі документів про освіту та дає змогу стороннім особам перевірити їх автентичність і цілісність без довіреного централізованого посередника. Система є P2P-мережею вузлів-валідаторів; кожен вузол зберігає повну копію ланцюга блоків. У ланцюгу зберігаються виключно хеш документа SHA-256, підпис емітента, ідентифікатор емітента, мітка часу та обмежені за розміром метадані.

Топологія: один вузол-валідатор на один заклад освіти (емітента). Кожен заклад має власну пару `issuer_id` / `IssuerKeyPair` і власну пару `node_id` / `NodeKeyPair`. Демонстраційна мережа: n = 4, f = 1.

**До меж системи належать:** вузол мережі (REST, WebSocket), модулі консенсусу PoW і PBFT, SPA, контур спостережуваності (Prometheus, Grafana) у складі docker-compose, окремий компонент симуляції атак.

**До меж не належать:** зберігання файлів документів; кваліфікований електронний підпис і статус кваліфікованої довірчої послуги; інтеграція з ЄДЕБО; відкликання документів; облікові записи користувачів (див. п. 6.2); HSM.

### 1.2 Зовнішнє середовище

| Учасник | Тип | Взаємодія із системою | Протокол |
|---|---|---|---|
| Емітент (заклад освіти) | Користувач | Подання хеша документа на видачу | HTTPS / REST через SPA |
| Верифікатор | Користувач | Перевірка документа за хешем | HTTPS / REST через SPA |
| Оператор вузла | Користувач | Розгортання, моніторинг | docker compose, Grafana (HTTPS) |
| Зловмисник | Модель загроз | Sybil-атака, backdating | REST, WebSocket |

Prometheus і Grafana є сервісами docker-compose у складі системи (SRS-FUN-59) і не належать до зовнішніх систем. Зовнішніх програмних систем, окрім браузера користувача, система не має.

## 2. Нормативні посилання

FIPS 180-4 (SHA-256); FIPS 186-5 (ECDSA); RFC 8446 (TLS 1.3); RFC 6455 (WebSocket); RFC 8259 (JSON); RFC 6962 (domain separation у дереві Меркла); Regulation (EU) 2016/679, ст. 5, 25; OWASP API Security Top 10 (2023); Castro, Liskov. Practical Byzantine Fault Tolerance, 1999.

## 3. Functional Requirements (Функціональні вимоги)

Позначення джерела: `LR4` — Core Features підрозділу 1.5.2; `AUD` — доповнення за результатами ШІ-аудиту; «Проєктне рішення» — вимога, що випливає з проєктування ядра та вузла; позначка † біля ідентифікатора — доповнення аудиту, яке підлягає підтвердженню на етапі реалізації (див. п. 11).

## 6. Обмеження, припущення, середовище

### 6.1 Обмеження проєктування

- Мова вузла: Python 3; фреймворк FastAPI; асинхронна модель asyncio.
- `src/blockchain_core` не повинен імпортувати `src/node`; ключі, `expected_difficulty` і `ValidatorSet` передаються як параметри.
- Транспорт між вузлами: REST та WebSocket; брокер повідомлень (RabbitMQ, Kafka) не застосовується.
- Сховище блоків: контракт `ChainStore` з бекендами JSON і SQLite (SRS-FUN-19).

### 6.2 Припущення та рішення щодо обсягу

- **Облікові записи та OIDC.** Читання (`GET`) публічне за своєю суттю: верифікатор не зобов'язаний довіряти вузлу, оскільки перевіряє Merkle proof і підпис локально. Автентифікація емітента виконується підписом `IssuerKeyPair` і реєстром емітентів, а не токеном користувача. Система не містить облікових записів користувачів, OAuth2/OIDC та JWT. Адміністративні операції виконуються оператором на рівні розгортання (docker compose).
- **mTLS не вимагається.** TLS забезпечує конфіденційність і автентифікацію сервера; ідентичність вузла підтверджується на рівні застосунку підписом `NodeKeyPair`.
- **Відкликання документів** не входить в обсяг: реєстр append-only, механізм відкликання не реалізується.
- **Хеш як псевдонімізовані дані.** Хеш документа, що містить персональні дані, розглядається як псевдонімізований; сіль не вводиться, оскільки верифікатор повинен відтворити хеш лише з файлу. Незмінність ланцюга обмежує право на видалення (GDPR, ст. 17); пом'якшення — зберігання лише хеша та підпису.
- **Відомі обмеження.** Заклад, що отримав хеш документа іншого закладу, може подати його від свого імені; Byzantine-primary може цензурувати записи, що пересилаються; відповідність `issuerN` ↔ `nodeN` забезпечується розгортанням; захисту від повтору блоків і голосів між незалежними розгортаннями з однаковими ключами та genesis немає, розгортання повинні використовувати різні ключі; відкат ланцюга до валідного префікса локально не виявляється (пом'якшення — SRS-FUN-68).
- **Годинники вузлів** синхронізуються хостом; допустимий зсув мітки часу нового блоку обмежується за SRS-FUN-65.
- **Поза обсягом:** 51 %-атака на PoW, DoS мережевого рівня, фізичний доступ до хоста, HSM.

### 6.3 Конфігурація вимірювань

Один хост; Windows 11 із Docker Desktop (WSL2); docker-compose; n = 4, f = 1; вузол обмежений за SRS-NFR-INF-04; генератор навантаження k6 — в окремому контейнері з виділеним `cpuset`. Модель процесора, кількість ядер та обсяг ОЗП хоста фіксуються в кожному звіті вимірювань. Для навантажувальних тестів PERF-01/02 параметр `RATE_LIMIT_PER_MIN` підвищується в конфігурації стенда; SRS-NFR-SEC-05 перевіряється окремо зі значенням за замовчуванням.

## 8. Glossary (Глосарій)

| Термін | Визначення |
|---|---|
| Latency | Час між надсиланням запиту та отриманням відповіді; у SRS вимірюється перцентилями (p95, p99). |
| RPS | Requests Per Second — кількість запитів за секунду. |
| PBFT | Practical Byzantine Fault Tolerance — алгоритм консенсусу, що допускає f візантійських вузлів у мережі з n ≥ 3f + 1 вузлів. |
| Proof of Work (PoW) | Консенсус на основі підбору `nonce`, за якого хеш блоку задовольняє цільове значення складності; фіналізація ймовірнісна. |
| `difficulty` | Кількість провідних нульових біт хеша блоку, що вимагається в PoW. |
| Merkle proof | Послідовність хешів сусідніх вузлів, що доводить належність запису до кореня дерева Меркла. |
| Hash-linking | Зв'язок блоків через включення хеша попереднього блоку в preimage наступного. |
| Backdating | Ретроактивна зміна запису в минулому: (а) модифікація існуючого блоку; (б) підроблена мітка часу нового блоку. |
| Sybil-атака | Створення фіктивних вузлів для набуття впливу на консенсус. |
| `ValidatorSet` | Статичний, заданий під час старту перелік валідаторів, за яким рахується кворум PBFT. |
| `IssuerRegistry` | Статичний реєстр відповідності `issuer_id` публічним ключам емітентів. |
| `PeerInfo` | Динамічний реєстр відомих вузлів для розсилки; не впливає на кворум. |
| Mempool | Черга підписаних записів, що очікують включення в блок. |
| Finalization | Стан блоку, за якого його скасування неможливе за моделлю консенсусу (PBFT — детерміноване, PoW — ймовірнісне). |
