## Матриця нефункціональних вимог (NFRs)

Конфігурація вимірювань: 4 вузли (n = 4, f = 1), docker-compose. Повна версія — [1_analysis.md](1_analysis.md#153-нефункціональні-вимоги-nfrs).

| Категорія | Вимога | Цільова метрика |
| --- | --- | --- |
| Продуктивність | Верифікація `GET /documents/{hash}` | p95 ≤ 200 мс при 200 RPS на вузол |
| Продуктивність | Фіналізація блоку PBFT | ≤ 2 с (n = 4, f = 1) |
| Масштабованість | Реєстрація записів | ≥ 50 записів/с, до 256 записів у блоці (структурна межа ядра — 500) |
| Безпека | Примітиви та транспорт | SHA-256, ECDSA P-256, TLS 1.3 |
| Безпека | Автентифікація запису | Лише підпис зареєстрованого емітента (інакше 403) |
| Комплаєнс | GDPR (ст. 5, 25) | У ланцюгу лише хеш, підпис, ідентифікатор емітента |
| Надійність | Fault Tolerance | PBFT: f ≤ ⌊(n − 1)/3⌋ збійних вузлів |
| Надійність | Стійкість до атак | Backdating виявляється у 100 % тестів; Sybil-вузли без реєстрації не впливають на консенсус |
| Інфраструктура | Контейнери та образи | Docker без root; Trivy: 0 CRITICAL |
| Супроводжуваність | Якість коду | Покриття ядра тестами ≥ 80 % |

Травень 2027 р. — нормоконтроль і передзахист.

**Експлуатаційна примітка.** Стан PBFT зберігається поруч із ланцюгом у файлі `<CHAIN_PATH>.pbft-state.json`. Видаляючи файл ланцюга, видаліть і його `.pbft-state.json`: за відсутності файлу стану на непорожньому ланцюгу вузол PBFT не стартує (fail closed), якщо не задано `PBFT_ALLOW_MISSING_STATE=true` (при цьому на кожному запуску пишеться попередження). Записані Byzantine-події зберігаються в цьому ж файлі й переживають перезапуск; зняти липкий статус `byzantine_event_detected` можна лише свідомо, запустивши вузол із `BYZANTINE_RESET_ON_BOOT=<токен>`. Токен — одноразовий дайджест: за кожного запуску зі збереженими Byzantine-подіями вузол пише WARNING з токеном скидання (перші 16 hex-символів SHA-256 від канонічного JSON списку збережених подій). Події скидаються лише якщо значення змінної дорівнює цьому токену (WARNING «operator reset»); будь-яке інше значення відхиляється з WARNING, а події лишаються, тож забута змінна не стере нових доказів (дайджест, а не кількість, бо кількість може збігтися після заміни подій у межах ліміту на порушника). Без змінної скидання немає. Після запуску змінну треба прибрати. Ключові файли вузла повинні мати права `0600`: на Windows bind-mount показує права `0777`, і контейнер Linux відхилить ключі — використовуйте іменовані томи або копіюйте ключі з `chmod 0600` (Slice 19).

## Key revocation runbook

Регламент для оператора мережі на випадок компрометації ключа вузла чи видавця (`ValidatorSet` / `IssuerRegistry`).

**Виведення з обігу та відкликання.**
- *Виведення з обігу* (`retired_at`) — звичайна ротація: старий ключ лишається придатним для перевірки того, що він підписав до `retired_at`, нові підписи ним не приймаються.
- *Відкликання* (`"revoked": true`) — ключ не розв'язується ні для якої позначки часу, тож усе, що ним підписано (також заднім числом, отримане через синхронізацію), стає недійсним.

**Коли відкликати.** Лише коли приватний ключ скомпрометовано. Для планової ротації чи виведення вузла використовують `retired_at`.

**Наслідки.** Ланцюг стає недійсним на кожному вузлі, починаючи з першого блока (або запису), підписаного цим ключем, — вузли показують `chain_valid = false` і `first_invalid_index`; мережа перестає нарощувати ланцюг. Вузол, чий власний ключ відкликано, не стартує. Якщо під час запуску відновлений ланцюг недійсний і відкликана особа підписувала історію не пізніше `first_invalid_index`, у журналі з'являється ERROR із її ідентифікатором і посиланням на цей регламент.

**Процедура** (оберіть один варіант):
1. Відкотити ланцюги на всіх вузлах до останнього блока перед першим підписом скомпрометованого ключа й повторно видати постраждалі документи.
2. Перевипустити ланцюг з генези (новий ланцюг, усі документи видаються повторно).

У обох випадках файли `ValidatorSet` та `IssuerRegistry` мають бути **однаковими на всіх вузлах**: розбіжні реєстри мовчки розгалужують ланцюг. Для вузла, ключ якого відкликано, додайте нову пару ключів: відкличений запис отримує `retired_at`, а новий запис із `valid_from` додається після нього. Файл ланцюга видаляється разом із `.pbft-state.json`.

`BYZANTINE_RESET_ON_BOOT` і `PBFT_ALLOW_MISSING_STATE` — разові дії оператора: задайте їх лише на потрібний запуск і одразу приберіть, інакше вони лишаються в силі й приховують нові проблеми.
