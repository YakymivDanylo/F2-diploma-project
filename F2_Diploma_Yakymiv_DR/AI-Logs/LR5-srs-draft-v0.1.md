# Специфікація вимог до програмного забезпечення (SRS)

**Система:** Децентралізована система верифікації документів на основі власної реалізації блокчейн-технології.
**Стандарт:** ISO/IEC/IEEE 29148:2018.
**Версія:** 0.1 (чернетка).

## 1. System Context (Контекст системи)

Система є розподіленою P2P-мережею вузлів, кожен з яких зберігає повну копію ланцюга блоків із записами про видані документи. У ланцюгу зберігаються лише хеш документа, підпис емітента та ідентифікатор емітента. Кожен заклад освіти керує одним вузлом-валідатором, демонстраційна мережа налічує 4 заклади (n = 4, f = 1).

**Межі системи (Scope):** вузли мережі, REST/WebSocket API вузла, SPA для видачі та верифікації, контур спостережуваності, компонент симуляції атак. До меж не належать: зберігання самих файлів документів, кваліфікований електронний підпис, інтеграція з ЄДЕБО.

**Зовнішнє середовище:**

| Учасник | Тип | Взаємодія |
|---|---|---|
| Емітент (заклад освіти) | Користувач | Видача документа через SPA / REST |
| Верифікатор | Користувач | Перевірка документа через SPA / REST |
| Оператор вузла | Користувач | Розгортання, моніторинг |
| Зловмисник | Модель загроз | Sybil, backdating |
| Prometheus / Grafana | Зовнішні сервіси | Збір метрик вузла |

## 2. Functional Requirements (Функціональні вимоги)

### 2.1 Ядро блокчейну

- **SRS-FUN-01.** Система повинна формувати блок із полями: індекс, мітка часу, хеш попереднього блоку, корінь дерева Меркла, nonce, та обчислювати хеш блоку SHA-256 за канонічною серіалізацією.
- **SRS-FUN-02.** Система повинна будувати дерево Меркла за записами блоку, генерувати та перевіряти Merkle proof.
- **SRS-FUN-03.** Система повинна підписувати хеш документа ключем ECDSA емітента та перевіряти підпис за зареєстрованим публічним ключем.
- **SRS-FUN-04.** Система повинна валідувати ланцюг: hash-linking, корінь Меркла, підписи та складність PoW.
- **SRS-FUN-05.** Система повинна зберігати блоки в append-only сховищі та відновлювати стан після перезапуску.

### 2.2 Консенсус

- **SRS-FUN-06.** Система повинна реалізувати Proof of Work з налаштовуваним difficulty.
- **SRS-FUN-07.** Система повинна реалізувати трифазний PBFT (pre-prepare, prepare, commit) для n ≥ 3f + 1.
- **SRS-FUN-08.** Система повинна перемикати алгоритм консенсусу конфігурацією вузла.

### 2.3 Мережа

- **SRS-FUN-09.** Вузол повинен надавати REST API: подання запису, пошук за хешем, отримання блоку, стан ланцюга, перелік вузлів.
- **SRS-FUN-10.** Вузол повинен розсилати блоки та повідомлення консенсусу за WebSocket, синхронізувати ланцюг і розв'язувати розгалуження.
- **SRS-FUN-11.** Вузол повинен експортувати метрики Prometheus.

### 2.4 Інтерфейс та експлуатація

- **SRS-FUN-12.** SPA повинна забезпечувати видачу документа, верифікацію за хешем та візуалізацію ланцюга.
- **SRS-FUN-13.** Система має розгортатися у N контейнерах через docker-compose з Prometheus/Grafana.
- **SRS-FUN-14.** Система має симулювати Sybil-атаку та backdating і реєструвати результати.

## 3. Non-Functional Requirements (Нефункціональні вимоги)

Конфігурація вимірювань: n = 4, f = 1, docker-compose, один хост.

| ID | Категорія | Вимога | Метрика |

## 5. Glossary (Глосарій)

| Термін | Визначення |
|---|---|
| PBFT | Practical Byzantine Fault Tolerance — консенсус, що допускає f візантійських вузлів із n ≥ 3f + 1 |
| Proof of Work | Консенсус на основі підбору nonce, при якому хеш блоку задовольняє цільовій складності |
| Merkle proof | Шлях хешів, що доводить належність запису до кореня дерева Меркла |
| Hash-linking | Зв'язок блоків через включення хеша попереднього блоку |
| Backdating | Ретроактивна зміна запису в минулому |
| Sybil-атака | Створення фіктивних вузлів для впливу на консенсус |
